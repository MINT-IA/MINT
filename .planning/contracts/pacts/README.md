# File-system Pact broker — `.planning/contracts/pacts/`

Phase 95 Plan 02 (TEST-02). Closes doctrine §7 ship-gate item « Pact contracts mobile↔backend verified green ».

## What is in this directory

- `mint_mobile-mint_backend.json` — Pact-v3 consumer-driven contract authored from the mobile side, declaring 4 interactions:
  - `POST /api/v1/anonymous/chat`
  - `POST /api/v1/coach/chat`
  - `POST /api/v1/documents/upload`
  - `POST /api/v1/onboarding/premier-eclairage`

Each interaction declares a request shape (method, path, headers, body) and a response shape (status, headers, body) with Pact `matchingRules` (type / regex / integer / decimal matchers — never literal values).

## Authoring approach

The contract file is **hand-authored** (not generated by `pact_dart`). Reason: the maintained `pact_dart` package on pub.dev (last release `0.8.0`, 2025-04) declares `http: ^0.13.3`, while `apps/mobile/pubspec.yaml` is on `http: ^1.2.0` — direct version conflict, `flutter pub get` fails. Per planner discretion (`95-02-PLAN.md` `<risks>` clause 1, fallback path), we use **snapshot-format Pact JSON** under this directory. The mobile-side consumer test (`apps/mobile/test/contracts/pact_consumer_snapshot_test.dart`) validates that the contract file:

1. Conforms to Pact-v3 schema (consumer / provider / interactions[]).
2. Lists interactions for the 4 endpoints the mobile app actually calls — verified by grepping `apps/mobile/lib/services/api_service.dart` and the related service files for matching path + body-key sets.

The backend-side provider test (`services/backend/tests/contracts/test_pact_provider_verification.py`) replays each interaction against the FastAPI app via `TestClient` and asserts that the live response matches the contract's response shape under the declared matching rules. **No Ruby `pact-provider-verifier` binary, no uvicorn subprocess** — pure Python loop using the existing TestClient pattern from `services/backend/tests/conftest.py`.

This is « consumer-driven contracts » per the Pact spec: the consumer authors the contract, the provider must satisfy it, drift is detected via `git diff`.

## Drift policy (CI-gated)

Both `flutter test test/contracts/` and `pytest services/backend/tests/contracts/` run in CI under the `pact-verify` job in `.github/workflows/ci.yml`. The job:

1. Verifies the consumer-side snapshot test passes (mobile call sites still match the contract).
2. Verifies the provider-side test passes (FastAPI live responses still match the contract).
3. Runs `git diff --exit-code .planning/contracts/pacts/` after both jobs — fails the build if anyone edited the JSON without rerunning local tests + committing.

Identical pattern to the existing `contracts-drift` job at `ci.yml:41` (regenerate + diff).

## When to update

- **Mobile changes the request body / headers / path** → edit `mint_mobile-mint_backend.json` AND make sure the consumer-side snapshot test still passes locally → commit both → CI re-verifies.
- **Backend changes the response body / status / fields** → CI provider verification fails → either revert the change or update the contract to track the new shape (consumer-driven, so change must be coordinated with mobile).
- **New endpoint added** → append a new interaction to `interactions[]`.

## Why file-system, not Pactflow

- **$0/mo** — Pactflow paid tier is $30/mo and out of MVP cost budget per doctrine §8.
- **Public repo** today (per `feedback_public_repo_discipline.md` until launch milestone) so contracts in-repo is acceptable.
- **1 consumer × 1 provider** — no fan-out broker need yet. Pactflow upgrade deferred to v2.16 post-launch when a second consumer (web client) lands.

## Doctrine alignment

- **Anti-test-theater (`2026-05-06-test-theater-post-mortem-doctrine.md` §1)** — contract is authored ONCE, on the mobile side, and verified by the backend independently. No « author-and-grade-same-session » loop: the mobile snapshot test does not consult the live backend, the backend verification does not consult the mobile source — they meet only at this committed JSON file.
- **Karpathy 3 (surgical changes)** — zero edits to `apps/mobile/lib/services/api_service.dart` or to the FastAPI endpoint handlers. The pact files + 1 mobile test + 1 backend test + 1 CI job are purely additive.
