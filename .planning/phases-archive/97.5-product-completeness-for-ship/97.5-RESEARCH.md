## A. Phase goal

When this phase closes, the canonical **chat-as-verb** trajectory on iPhone 17 Pro
against Railway staging — cold launch → LandingScreen `Continuer sans compte` →
`/home` → CapDuJourBanner tap → MintCardActionBar `Explique-moi` →
**MintChatOverlay opens with a populated coach opener** — runs end-to-end with :

1. A non-empty overlay body carrying a coach opener message (NarrativeSleeveCard
   rendered if the source_card has facts ; bare narrator text otherwise).
2. A FR-human header label aligned with `VOICE_SYSTEM.md` (no raw enum leak).

   the staging `COACH_CITATION_GATE_ENABLED=True` flag).
4. The five `SessionReport` fields SOT §2 says are NOT YET IMPLEMENTED
   (`confidenceScore`, `chiffreChoc`, `alertes`, `simulationAssumptions`,
   `generatedLetters`) wired so the SoA artefact is contract-complete per
   Phase 97 D-30 ship-gate.
5. Consent receipts captured for `TRANSFER_US_ANTHROPIC` + `PERSISTENCE_365D`
   on the coach-chat write-path and `VISION_EXTRACTION` on the documents
   upload path (LSFin HARD BLOCKER #1 from the 2026-05-12 panel —
   `.planning/decisions/2026-05-12-maestro-golden-day-flow-PANEL.md` §C6).
6. At least 2 production Aujourd'hui cards (CapDuJourBanner is row 1 — already
   wired ; row 2-N comes from `PHASE97_AUJOURDHUI_CARD_INVENTORY.md`) carry a
   functional `MintCardActionBar` such that the 3-verb intent bar is reachable
   from cold launch on multiple surfaces, not only the cap-du-jour banner.
7. **L2 alembic-Postgres dry-run job wired and blocking on every PR** — every
   future alembic migration is validated against an ephemeral `postgres:15`
   container at PR-time, catching the schema-shape regression class
   (truncation, syntax, type mismatch, FK ordering) that broke staging
   2026-05-12T11:14Z (35-min `502` outage).

**product layer** (P004/P002/P001/SessionReport/Consent) plus the

## D. Risk analysis (failure mode per perimeter)

### D.1 P004 — risk : auto-fire UX feels wrong

**Failure mode :** Auto-firing turn 1 on every overlay open burns the user's
3-turn budget immediately. If the user tapped « Explique-moi » by accident,
they've lost 1/3 turns before reading anything.

**Mitigation :** The opener should be FREE (not counted as turn 1). Two
patterns are valid : (a) server-side turn_cap.py exempts the « opener »
turn from the counter — a new query param `is_opener: bool = False` ; or
(b) the opener is a backend-precomputed cached response served WITHOUT
calling Claude (zero LLM cost, zero turn debit). Pattern (b) is preferable
per Karpathy #2 simplicity-first — the opener is a templated
NarrativeSleeve with `metaphor_lookup` filling the metaphor slot. No
Claude call needed.

**Verification :** R3 smoke flow asserts the turn counter shows `0 / 3`
after the overlay opens (user's first send becomes `1 / 3`).

### D.2 P004 — risk : « tests passing ≠ feature working » trap

**Failure mode (the canonical 0-trust trap, §9 CLAUDE.md) :** R2 ships P004
with a unit test asserting `_chatMessages.isNotEmpty` on initState, all CI
green ; but on Julien's sim the auto-fire silently returns 400 and the body
stays empty. The Maestro flow passes because it only checks structural
visibility (overlay opens, ID present), not semantic content. This is the
**exact pattern** that surfaced D1 on 2026-05-12T19:30Z.

**Mitigation :**
1. The R2 PR MUST include a Maestro flow extension that asserts
   `assertVisible: { id: narrative_sleeve_card }` OR text content like
   `« Voyons ensemble »` (the HOOK_FALLBACK) appears in the overlay body
   within 5 seconds of overlay open. Pure structural assertion is not
   sufficient — semantic content must be locked.
2. Pillar 0.a SCOUT discipline (per `.planning/MINT-DEBUG-METHOD.md`) :
   after each R2 perimeter PR merges to dev → staging deploy → manual
   SCOUT walkthrough → `_SESSION-YYYY-MM-DD-OBSERVED.md` with
   screenshot + verdict.
3. CLAUDE.md §9.6 receipt format applied : every R2 status claim cites
   `Evidence: <file path / sim snapshot / sha>` + `Caveat: <what NOT
   checked>`.

### D.3 ConsentService — risk : fail-CLOSED breaks existing users

**Failure mode :** R2 ships the gate fail-CLOSED, but the consent table is
empty for existing staging + prod users (they signed up before the granular
consent was introduced). Every authenticated `/coach/chat` call returns 403.
Massive user-visible breakage.

**Mitigation :**
1. **Soft-launch flag** : `CONSENT_GATE_ENFORCEMENT_MODE = "log_only" |
   "soft_block" | "hard_block"`. Default to `log_only` on staging for the
   first 24h ; promote to `soft_block` (returns 200 but renders a
   non-blocking warning + Sentry breadcrumb) once the migration of existing
   users to default consents has run ; promote to `hard_block` only when
   all metrics are clean.
2. **Migration script** : `tools/migrations/grant_default_consents_existing_users.
   py` that grants `TRANSFER_US_ANTHROPIC` + `PERSISTENCE_365D` for every
   existing user with an `accepted_terms_at` timestamp, on the basis that
   pre-granular T&C covered these (LSFin / nLPD legal continuity argument).
3. The migration must be re-runnable and idempotent (`grant_nominative`
   already supports idempotency per `consent_service.py:93`).

### D.4 SessionReport — risk : Pydantic v2 forward-reference break

**Failure mode :** Adding 4 new sub-models (`EnhancedConfidence`,
`ChiffreChoc`, `Alerte`, `GeneratedLetter`) inside `session.py` triggers a
forward-ref resolution issue or import cycle with the rest of the schema
modules. The existing 6586 backend tests start failing for unrelated reasons.

**Mitigation :**
1. Each sub-model in a separate file under `services/backend/app/schemas/`
   (e.g. `enhanced_confidence.py`, `alerte.py`) ; `session.py` imports
   them.
2. Pydantic v2 `model_rebuild()` if needed.
3. Run `pytest services/backend/tests/test_session_report_completion.py
   tests/test_session_report*.py` (existing) before pushing.
4. Karpathy #3 surgical : only `session.py` + 4 new sub-model files +
   1 new test file touched. No producer code modified in R2.

### D.5 P002 — risk : iOS Semantics drift (M001)

**Failure mode :** Wiring more cards with `Key('card_<kind>')` reproduces
the M001 anti-pattern (Flutter Keys don't propagate to iOS Semantics
identifiers). Maestro flows authored in R3/R4 can't target the new cards
without falling back to accessibilityText regex (the current S005 workaround).

**Mitigation :**
1. R2 P002 work MUST wrap each card root in `Semantics(identifier:
   'card_<kind>', child: ...)` per the recommended M001 fix (registry line
   204).
2. The fix is mechanical and well-understood — apply across all newly-wired
   cards in the same PR.

### D.6 Railway deploy regression risk

**Failure mode :** Today (2026-05-12) saw 2 staging deploy regressions :
iOS entitlement provisioning + alembic length issue. Adding new alembic
migrations (e.g. for consent backfill) or schema changes (SessionReport)
to R2 risks compounding. A single bad migration head locks the staging
deploy chain.

**Mitigation :**
1. `tools/checks/alembic_revision_length.py` (L1, PR #577) lints
   migration name length pre-commit. Today's 36-char offender is caught.
2. **L2 (B.6) is the upgraded mitigation** : on every PR with any alembic
   touch, the GitHub Actions job spins up `postgres:15` and runs
   `alembic upgrade head` + `downgrade base` + `upgrade head` idempotency.
   The L1 lint catches length-class bugs ; L2 catches the broader
   schema-shape class (truncation, FK ordering, type mismatch, Postgres
   syntax). With both in flight, today's Railway outage class is
   prevented mechanically.
3. SessionReport changes are SCHEMA-ONLY (Pydantic), not Alembic — zero
   database migration.
4. ConsentService gate doesn't need an alembic migration (the table exists ;
   only data backfill via Python script).
5. Test on staging in isolation per perimeter PR ; never bundle two schema
   changes in one PR.

### D.7 Doctrine drift risk

**Failure mode :** P004's « auto-fire opener » could slip back toward
chat-first onboarding (e.g. opener becomes « Hi! Tell me your age and
canton ») — which the v2.9 milestone REJECTS (`MILESTONE-CHAT-AS-VERB-
2026-05-09.md` §Strategic frame + panel synthesis C1).

**Mitigation :**
1. Opener copy contract : the opener acknowledges the **card** (source_card
   facts), not the **user** (no profile questions). Examples :
   « Voici ce qui change avec ton cap du jour. Tu veux comprendre le
   « pourquoi » ou voir les chiffres ? »
2. R2 PR review checklist : opener copy must NOT contain any of « âge »,
   « canton », « salaire », « profil » as a question-form construct.
   Lint candidate : `tools/checks/no_onboarding_drift_in_openers.py` (small
   regex sweep).

### D.8 L2 — risk : false sense of coverage

**Failure mode (per L1-L5 ADR §counter-arguments) :** L2 ships and the team
treats every alembic-Postgres regression class as « covered ». But L2's
ephemeral `postgres:15` container has **empty tables** when `alembic upgrade
head` runs. Today's B023b migration includes an orphan-DELETE step ; on
empty tables that step is a no-op and L2 passes. On prod-shape data, an
orphan-DELETE may trip a long-running lock, an FK violation, or a
constraint-deferred error. Same risk class for any data-mutating migration
(backfills, NULL → default casts, ENUM value renames against existing rows).

**What L2 covers :**
- Truncation (today's 36-char revision_id — caught) ✓
- Postgres-vs-SQLite syntax (JSONB vs JSON, generated columns) ✓
- FK ordering errors (create tables in wrong order) ✓
- Type mismatch on `server_default` (cast errors, default-value drift) ✓
- Migration idempotency (downgrade base + upgrade head must round-trip) ✓

**What L2 does NOT cover :**
- Data-level race conditions (concurrent writes during migration) ✗
- Production-shape data behaviours (backfill timing, lock duration) ✗
- ORM-level Postgres-specific behaviour beyond alembic (covered by L3) ✗
- Application-level regressions caused by the migration (covered by L3+L4) ✗

**Mitigation :**
1. The PLAN.md success criteria for L2 MUST state explicitly « L2 covers
   the schema-shape regression class ; L3 + L4 + production-shape data
   fixtures address data-level race conditions ». No over-claim.
2. The L2 verification flow (B.6 fix-shape step 2) intentionally tests
   ONLY the schema-shape class. Data-level regression tests are NOT in
   scope for R2 ; they belong to L3 (R4 or v2.10).
3. The L1-L5 ADR is the authoritative reference. PLAN.md cross-links it.

**Counter 1 : « R2 is over-scoped — P004 alone closes the v2.9 doctrine
gap ; the other 5 perimeters can move to v2.10. »**

Steelman : the value-prop of v2.9 is the chat-as-verb pivot (« kill chat-tab,
cards become home, every tap surfaces a 3-turn coached overlay »). The ONLY
failure mode that breaks this prop in the user's eyes is the empty overlay
(P004). The other 5 perimeters are :
- P002 = coverage breadth (one card is enough to demo the pivot)
- P001 = backend-only compliance (already shipped at 18-22% per Julien GO)
- SessionReport = SoA artefact completeness, not the chat trajectory
- ConsentService = compliance posture, not user-facing functionality
- L2 = CI infrastructure, not user-facing

So one could argue R2 = P004 only and the rest moves to v2.10.

**Counter-counter :** The panel synthesis C4 (« tests of features that don't
exist ») is the canonical refutation for the product layer. R3 (smoke flow)

tests. Plus L2 is independently justified by the L1-L5 ADR : today's 35-min
staging outage cost 2 emergency PRs (#575 + #576). L2's 1-day investment
prevents recurrence of the entire schema-shape regression class. The
cost-benefit is overwhelming. The 6 rows are coupled to **shipping the
milestone safely**, not just to shipping the **demo**.

**Counter 2 : « ConsentService work belongs in a dedicated compliance phase,
not in a product-completeness phase. »**

Steelman : LSFin / nLPD compliance is its own discipline ; mixing it with

**Counter-counter :** The panel locked Consent as a hard blocker tied to the

**Counter 3 : « Auto-firing an opener turn that doesn't count against the

Steelman : v2.9 doctrine says « 3-turn cap per (user_id, source_card_id) ».

**Counter-counter :** The cap is a **user-driven** budget. The opener is

server-derived ; the doctrine survives.

**Counter 4 : « L2 belongs in R3/R4 (infra/CI), not R2 (product

Steelman : the R-perimeter sequencing ADR (julien-go 2026-05-12T09:55Z)

## G. Sequencing recommendation

The natural sequence after panel verdict + julien-go ADRs (R-sequencing +
L1-L5) + SCOUT pass :

### G.1 Proposed execution order

### G.2 Rationale for ordering

**Why P004 first (not parallel) ?**

The opener-pattern decision (templated vs LLM, free turn vs counted) is a
**foundational contract** that the other 4 product perimeters reference.
ConsentService needs to know whether the opener is a Claude call
(TRANSFER_US_ANTHROPIC fires on opener) or templated (no transfer, no
gate fires on opener). P002's per-card opener content depends on the
per-card SerializedCardContext shape that P004 nails down. Ship P004 first,
merge to dev, then unblock the other 4 product perimeters. L2 is the
exception — it's pure infra with zero coupling to the opener decision,
so it does not wait on P004.

**Why ConsentService parallel with SessionReport AND L2, not serial ?**

All three are independent of each other in code : ConsentService touches
`coach_chat.py` + `documents.py` + a new `consent_guard.py` ;
SessionReport touches `schemas/session.py` + new sub-model files ; L2
touches `.github/workflows/` + a docs file. No shared file. The Julien
GO ADR's « full autonomy » mandate authorises parallel sub-agent work.
Memory `feedback_no_micro_pauses` (« pack each turn with as many tool
calls as the dependency graph allows ») applies.

**Why L2 in slot 2-bis (not its own wave) ?**

The L1-L5 ADR targets L2 for « Phase 97.5 R2 » explicitly. Putting it in
slot 2-bis (parallel with slot 2-3) is the dependency-graph-honest place ;
no perimeter blocks it, it blocks no perimeter. Sequencing it later would
serialise the calendar against today's freshness.

**Why P002 after P004 even though independent in code ?**

Cosmetic + value-graph reason : merging P002 to dev when P004 is still in
flight means the SCOUT walkthrough on dev shows MORE empty overlays. That's
a bad feedback loop. Hold P002 until P004 is in dev, then wire 2 more cards
and watch ALL of them open populated.

**Why P001 last ?**

Pure paperwork. Can land in any cycle. Last because nothing depends on it.

### G.3 Calendar projection (working days)

Per panel synthesis estimate of 4-6 days for R2, L2's 1-day cost absorbed
in parallel with slots 2-3 :

| Day | Activity |
|---|---|
| Day 1 | P004 (Dart + backend opener + ARB + D2 label) — PR opened end-of-day |
| Day 2 | P004 review + merge to dev ; staging deploy ; SCOUT pass on staging ; **L2 PR opened** (slot 2-bis, ~1 day total) ; if D1 fixed, slots 2-4 can launch |
| Day 3 | ConsentService gate (slot 2) + SessionReport schema (slot 3) **in parallel** ; both PRs opened ; L2 PR review + verification-flow receipt + merge to dev |
| Day 4 | P002 (slot 4) wiring 2 more cards ; slots 2-3 merge ; P001 paperwork PR ; branch-protection update for L2 status check |
| Day 5 | All R2 PRs merged ; staging deploy ; SCOUT pass on full R2 ; if clean, R2 close-out |
| Day 6 (slack) | Recovery day for Railway deploy regressions or M001 fallout |

This fits within the panel-projected 4-6 day window for R2 + matches the
larger 4-week ship calendar in the synthesis. L2's 1-day cost is absorbed
in the parallel slot, not appended serially.

### G.4 Challenge to this sequencing

Could the planner usefully reorder ? Three valid alternatives :

1. **ConsentService first, P004 second.** Justification : the LSFin HARD
   BLOCKER is the highest *compliance-risk* item ; shipping P004 first means
   1-2 days of staging traffic through Anthropic without proper consent
   capture. Refutation : staging traffic is internal QA only (Mac mini +
   Julien sim) ; the LSFin exposure is bounded ; user-visible value (P004) is
   the operationalised priority. Stay with the recommendation.

2. **SessionReport first.** Justification : the panel singled out
   « SessionReport gap is the REAL ship blocker, not Maestro coverage »
   (verdict matrix row 2). Refutation : « ship blocker » in the SoA contract
   sense, not in the user-experience sense. The SoA artefact is only
   surfaced at end-of-session, not on every chat turn. P004 is the
   per-tap defect. Stay with the recommendation.

3. **L2 first.** Justification : today's staging outage is fresh ;
   prevent another one before any product work touches alembic. Refutation :
   no R2 perimeter as scoped touches alembic at all (SessionReport is
   Pydantic-only ; ConsentService gates against the existing
   `29_02_consents_granular` migration without a new one). L2's value is
   prophylactic for the broader codebase, not for R2 itself. Slot 2-bis
   (parallel) is honest sequencing ; bumping it to slot 1 would
   unnecessarily delay P004 (the highest-impact user-visible fix).
