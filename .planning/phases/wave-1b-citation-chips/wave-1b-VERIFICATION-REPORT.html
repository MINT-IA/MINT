Root cause (consensus across 3 specialist agents, 2026-05-15 panel on PR #627): the initial hypothesis (« empty intents → empty allowed_tools ») was wrong. The narrator IS advertised tools; the LLM has tools available but elects not to use them. Three converging findings (engram obs-1ba08390 backend-architect / obs-240cd512 ai-engineer / obs-8e55517a python-pro):

  • Proximate cause — tool_choice={"type": "auto"} at services/backend/app/services/rag/llm_client.py:227. The author's own comment at llm_client.py:222-224 literally admits the failure mode: « Sonnet sometimes skips tool_use entirely even when the system prompt says MANDATORY call save_fact. ». With "auto" the model is free to skip tool_use; with {"type": "any"} the API forces at least one tool call (per Anthropic spec). The 2-line fix never landed.
  • Compounding cause — no MANDATORY-tool-invocation directive in always-on bundle prompts. grep MANDATORY|invoque|Tu DOIS|tool_use on services/backend/app/services/coach/bundles/life_event_router.py and compliance_narrator.py returns ZERO matches. LifeEventRouterBundle.allowed_tools = ["get_budget_status", "get_retirement_projection"] (life_event_router.py:133-136) but the bundle's prompt_fragment never instructs the narrator to invoke them. The LLM treats the tools as optional.
  • Compounding cause — refusal escape hatch at services/backend/app/services/coach/citation_grammar.py:86-89: « En l'absence de clé adaptée pour un chiffre, écris ‘je n'ai pas cette donnée pour l'instant’ à la place du chiffre. » combined with claude_coach_service.py:660 « Ne cite JAMAIS un chiffre que tu ne peux pas sourcer depuis le contexte fourni ». The LLM is given an explicit refusal path BEFORE being told to invoke a tool. The forced-tool-invocation gate described in memory project_coach_forced_tool_invocation (« REJECT + re-prompt if LLM produces a number without a tool call trace ») is NOT wired.
  • Test gap: services/backend/tests/test_coach_tools_parity.py:238 calls _compute_budget_status(...) directly — tests the dispatcher math, not whether the narrator actually emits tool_use. tests/bundles/test_bundle_compiler.py:107 asserts the 2 always-on bundles activate but NOT that allowed_tools contains a chip-emitting tool. The invariant « typical user messages must yield ≥1 citation-emitting tool advertised AND emitted » is uncovered.

Distinguishing experiment (10 lines of python, no staging deploy): replay probe v7 directly against the Anthropic API twice with the same bundle-compiled prompt + tools, only tool_choice differs — auto baseline vs any variant. Variant returns stop_reason=tool_use with ≥1 tool_use block ⇒ single-line fix at llm_client.py:227 + bundle prompt fragments. Variant still text-only ⇒ doctrine rewrite (kill the refusal escape hatch + wire the forced-tool-invocation gate per project_coach_forced_tool_invocation).

Scope: this is NOT a Wave 1b code bug. Wave 1b adds citation chips on TOP of a working tool-call response. If the tool doesn't fire, there's nothing to cite. The bug lives in Wave 1a / coach orchestration territory (specifically the tool_choice disposition + bundle prompt fragment construction).
