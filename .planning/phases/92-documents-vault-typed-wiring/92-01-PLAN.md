# Phase 92 — Plan 01: Documents Vault Typed Wiring (DOCS-01 / DOCS-02 / DOCS-03)

## Goal

Close BUG #4 (P0, walkthrough audit 2026-05-06) by wiring the vault upload pipeline to merge typed `LppExtractedFields` into `CoachProfile`, invalidating confidence + recomputing Cap, and replacing the random-UUID `Idempotency-Key` with a deterministic SHA256-of-bytes so retries actually dedupe on the backend.

Single plan because the three sub-requirements share one test surface (vault upload golden test) and touch tightly-coupled code (one converter, one screen wire, one HTTP header). Splitting would force shared fixtures across plans for no isolation gain.

```dart
/// DOCS-01 (Phase 92) — Typed adapter so the vault upload path can reuse
/// the same merge engine as the /scan path. Wraps updateFromLppExtraction
/// to keep a single source of truth.
Future<void> updateFromLppExtractedFields(LppExtractedFields fields) async {
  final List<ExtractedField> bridged = <ExtractedField>[];
  void add(String fieldName, String label, double? value, String profileField) {
    if (value == null) return;
    bridged.add(ExtractedField(
      fieldName: fieldName,
      label: label,
      value: value,
      confidence: 1.0, // Backend extractor confirmed
      sourceText: 'vault_upload',
      needsReview: false,
      profileField: profileField,
    ));
  }
  add('avoir_vieillesse_total', 'Avoir LPP total', fields.avoirVieillesseTotal, 'avoirLppTotal');
  add('avoir_obligatoire', 'LPP obligatoire', fields.avoirObligatoire, 'lppObligatoire');
  // … one add(...) per row of the table above …
  await updateFromLppExtraction(bridged);
}
```

## Risks

**Headline risk : converter mapping drift.** If the LppExtractedFields → profileField table above is wrong, the vault upload silently writes wrong CHF values into CoachProfile and the « 1 CHF tolerance » test passes against the wrong golden (because both sides drift together). **Mitigation** : the converter test in `coach_profile_provider_lpp_extracted_fields_test.dart` asserts against constants extracted manually from `test_extractor_julien_cpe_golden.py` (70376.60, 91967.0, 539413.70). If the backend golden ever changes, the Flutter test fails and forces re-anchoring. **Do NOT** import golden values from a shared fixture — duplicate them as in-test constants so a backend regression can't paper over a converter bug.

Secondary risks:

- **Cap recompute thrash** — `MintStateProvider.recompute` runs the engine + caches `PrecomputedInsightsService`. After a vault upload it will run once. If the upload fires multiple times (multipart retry on flaky network), recompute also fires multiple times — acceptable per existing mint_state_provider.dart guarding (`_isRecomputing` flag). No mitigation needed.
- **`tauxConversionEnveloppe` dropped** — third conversion rate has no `profileField` mapping in the existing switch (lines 1385-1410). v2.14 lives without it ; documented as `// TODO(v2.15)` in the converter. Risk is purely informational, no behavior change.
- **MultipartFile.fromBytes filename** — switching from `fromPath` to `fromBytes` requires explicitly passing `filename`. If the backend logs/parses filename, behavior changes. Verified by reading `documents.py:405-435` — backend uses MIME parsing on bytes, filename is informational. Pass `file.uri.pathSegments.last` to keep parity.
- **Backend dedup activation** — once SHA256 keys land, a user re-uploading the exact same file will get `X-Idempotent-Replay: true` from the backend (documents.py:419) instead of a fresh extraction. This is the **intended** v2.14 behavior and matches the architecture audit concern #4. No user-visible regression : the cached `DocumentUploadResponse` is byte-identical to a fresh one.
