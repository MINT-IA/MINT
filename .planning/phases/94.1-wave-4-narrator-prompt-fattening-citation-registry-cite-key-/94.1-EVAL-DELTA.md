## Scoring contract caveat (per CLAUDE.md §9.5)

The 0/10 gate_correct in the **uncited_number** and **banned_claim** categories does NOT mean the gate is broken. It means the SCORING CONTRACT is rigid in a way that masks the gate's correct behavior :

- A fixture with `expected_gate_outcome = "rejected_uncited"` expects the narrator's FIRST-CALL output to trigger the gate's `REJECTED_UNCITED` verdict.
- In practice (verified by inspecting record `cit-21` of `94.1-eval-sonnet-gate-on.json` with `uncited_numbers_count=12`) :
  1. The narrator emits naked digits on the first call.
  2. The gate correctly detects them and returns `REJECTED_UNCITED` + retry_needed=True (matches expected).
  3. The retry-once call is fired with the D-09 reprompt addendum.
  4. The narrator STILL emits naked digits on the retry.
  5. The gate per D-08 collapses to `FALLBACK` on second uncited (this is the contract).
  6. The recorded `gate_verdict` is `fallback` — does NOT match the fixture's `rejected_uncited` expectation.

This means **the gate IS rejecting uncited numbers correctly** on the first call, but the post-retry verdict (recorded in the JSON) overwrites the first-call verdict. The fixture scoring would need to record EITHER the first-call OR a separate "any_rejection_observed" boolean to surface the underlying gate behavior. This is an EVAL-HARNESS scoring upgrade for 94.2, NOT a gate bug.

**Conservative interpretation:** if we re-scored with "first-call verdict matches expected" semantics, Sonnet uncited_number would be 8/10 correct (8 first-call REJECTED_UNCITED that were RE-MET by D-08 collapse) and banned_claim would be 7/10 correct (same logic). Combined with the valid_citation 9/20 → **Sonnet would be 24/50 = 48% gate_correct under the alternative scoring**. Same for Haiku : valid_citation 10/20 + uncited 6/10 (first-call detects) + banned 6/10 first-call → **22/50 = 44%**.

These alternative numbers are NOT the official measurement — they are a hypothesis about why the topline understates the improvement. The official numbers are the 20% in both models per the JSON aggregates above.

## Root cause hypotheses for 94.2 (NOT auto-iterating)

Per `94.1-01-PLAN.md` failure_handling section : surface to orchestrator for GO/NO-GO on iter 2. The candidate hypotheses (ordered by my confidence) :

### H1 (high) — Key list too long ; the narrator skims 18 bullets and forgets specifics

The grammar fragment lists 18 keys with their FR descriptions. Total bullet section is ~1.3 kB ; the narrator's attention may dilute over the list. 94.2 candidate change : group keys by INTENT (3a / lpp / tax / mortgage) so the bullet list is shorter per intent, surfaced ONLY when that intent is active. Cost : bundle-path complexity ; legacy-path stays the same. Test : eval-harness intent slicing.

### H2 (medium) — Examples too narrow

The fragment shows ONE cited example (`r3a_plafond_salarie_2026`) — the narrator may not generalise to other keys. 94.2 candidate change : expand to ≥6 examples covering ≥3 different keys × 2 surface contexts (sentence-end vs mid-sentence). Cost : fragment grows to 6-7 kB. Test : new fixtures targeting unseen keys.

### H3 (medium) — D-09 reprompt addendum does not match the fragment grammar verbatim

The first-call grammar fragment says « place `{{cite:<clé>}}` directement après le chiffre ». The D-09 reprompt (`citation_parser.REPROMPT_ADDENDUM_UNCITED`) says « Cite chaque chiffre via `{{cite:<key>}}` ou ne l'émets pas ». The key word « clé » vs « key » + the punctuation around it may confuse the narrator. 94.2 candidate change : align both strings verbatim (use « clé » everywhere, or pick a canonical FR vocabulary across system prompt + retry reprompt). Cost : 2 string edits in `citation_parser.py`. Test : test_grammar_consistency_between_prompt_and_reprompt.

### H4 (low-medium) — `_CITATION_ADJACENCY_CHARS = 80` is too tight in some cases

The narrator may emit `{{cite:<key>}}` somewhere in the sentence but more than 80 chars from the number. Without inspecting raw responses (PII-clean ones), I can't quantify this. 94.2 candidate diagnostic : log placeholder placement distance per fixture in the JSON aggregate. Cost : 5 LOC in `citation_parser.gate`. Test : test_adjacency_distribution_in_aggregate.

### H5 (low) — The model is genuinely ignoring the system prompt for the « emit a number without citing it » default

Hypothesis : in instruction-tuned LLMs, default behavior is to be helpful and concrete (give numbers) ; the « cite or don't emit » directive is novel and may fail at scale. If H1-H4 don't lift the rate, this is what we'd be left with — and the right move is either (a) accept ≤50% gate-correct as the upper bound and decide on the flag flip with that data, or (b) escalate to a few-shot in-context fine-tune (per-prompt examples), which is much more invasive.
