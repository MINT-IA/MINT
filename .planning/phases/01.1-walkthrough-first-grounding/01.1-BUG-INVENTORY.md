## F-01.1-01 — Coach « Erreur de connexion » (REFRAMED P0)

**Original guess (Wave 3 OBSERVATIONS.md) :** coach-runtime backend regression sur `/api/v1/anonymous/chat`.

**Real root cause (confirmed 2026-05-21 via Passe A) :** Le sim avait une **DEBUG build** installée qui pointe **`http://localhost:8888/api/v1` par défaut**. Aucun backend localhost ne tourne → connection refused → primary path catch → anonymous fallback (aussi vers localhost) → `_anonymousFallback(errorType: 'network')` retourne `message: ''` → `anonMsg.isEmpty` → UI affiche `coachErrorConnection` (« Erreur de connexion. Vérifie ta clé API. »).

**Backend marche, c'est le client qui parle à la mauvaise URL.**

### Why « régression encore une fois » (Julien)

Cette classe de bug est **récurrente** parce qu'elle a 2 origines structurelles :

1. **Discipline build** : memory `feedback_app_targets_staging_always.md` dit « sim/walker MUST hit staging », mais aucune sauvegarde mécanique n'empêche un `flutter run` ou `flutter build ios --debug --simulator` sans `--dart-define`. Le développeur (ou un agent) qui oublie le flag installe une build qui tape localhost mort.
2. **Candidate ordering en release** : `mint-production-3a41.up.railway.app/api/v1` est premier en release. Production n'a PAS `/api/v1/anonymous/chat` déployé (curl probe → **HTTP 404**). Donc même une release-build TestFlight qui ne passe pas par walker.sh pointerait sur production → 404 → même erreur exactement.

→ Memory `feedback_anthropic_key_on_railway.md` confirme que le triage historique sur « coach unavailable » a souvent dérivé vers Railway env (faux suspect). Le vrai vecteur a TOUJOURS été : config baseUrl baked-in à la build.

### Production 404 evidence

```
$ curl -X POST https://mint-production-3a41.up.railway.app/api/v1/anonymous/chat \
    -H 'Content-Type: application/json' \
    -H 'X-Anonymous-Session: 12345678-1234-4234-8234-123456789012' \
    -d '{"message":"test"}'
HTTP=404

```

Production health OK (HTTP 200, `{status:ok}`) mais l'endpoint anonymous-chat n'est pas déployé. Cohérent avec memory `project_no_real_prod_yet` (« staging = test loop, no real users »).

### Severity

**P0** — bloque TOUT démo coach. Pas juste le hero flow Wave 3 — n'importe quel TestFlight tester / journaliste / Julien lui-même sur son sim non-walker-build voit ce bubble dès la 1ère question.

### Escalation

- **Layer A (build discipline)** : sub-phase 01.1 — j'enchaîne dans la même session (Passe B-1, 15 min). Rebuild via walker.sh, reinstall, re-run maestro test → verify hero flow exit 0.
- **Layer B (code fix anti-regression)** : sub-phase 01.4 coach-runtime audit — surgical patch sur `ApiService._baseUrlCandidates` + `ensureReachableBaseUrl()` pour que debug mode tombe sur staging fallback si localhost mort. 1 PR, ≤80 lignes.
- **Layer C (prod gap)** : décision strategy — déployer `/anonymous/chat` sur production OU documenter explicitement « production ne sert pas anonymous, TestFlight cible staging ». Reporter à Julien. Pas dans le scope sub-phase 01.1.

## Counter-arguments (CLAUDE.md §8 wiki schema)

- **« Pourquoi pas juste rebuilder ? Le code marche peut-être déjà sur staging. »** — Layer A seul est insuffisant car n'importe quel agent futur qui lance `flutter build ios --debug` sans dart-define re-tombera sur le même bug. Layer B (code fix) est ce qui rend la discipline mécanique.
- **« Pourquoi pas re-déployer production avec `/anonymous/chat` ? »** — Memory `project_no_real_prod_yet` dit production n'est pas le test loop. Déployer l'endpoint sur production introduirait du surface attack avant qu'on soit prêt à scaler. Mieux : documenter explicitement que TestFlight cible staging (memory `project_testflight_ship_path` le dit déjà mais pas dans le code).
- **« Pourquoi flagger F-01.1-06 si le LLM est trained pre-2025 ? »** — Le pivot « lucidité, pas protection » repose sur la citation gate. Un coach qui cite des constantes 2024 quand la backend serve 2025 = trust collapse sur le PREMIER message. Pas négociable.
