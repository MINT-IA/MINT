## Decisions Made

1. **Used `applyFromMap` (existing convention) instead of `applyFromConfig` (PLAN.md cited name).** The PLAN cited `applyFromConfig` in 3 places (task 1 step 1.2, threat T-01.5-45, success criterion 2) but the actual method name in `feature_flags.dart:129` is `applyFromMap` — used by 11 existing flags (enableCouplePlusTier, enableSlmNarratives, enableDecisionScaffold, valeurLocative2028Reform, safeModeDegraded, enableOpenBanking, enablePensionFundConnect, enableExpertTier, enableAdminScreens, enableMvpWedgeOnboarding, chatTabVisible). Following the existing convention is non-negotiable; the PLAN name was a documentation error (PLAN was written based on a stale grep). Documented as deviation Rule 1 below.

2. **Added `debugCoachHardGateWarningHook` instead of mocking sentry_flutter.** Rationale: the codebase has NO precedent for `Sentry.captureMessage` mocking (the existing convention `MintBreadcrumbs` wraps `Sentry.addBreadcrumb` — different SDK surface, no-op without SDK init, NOT used by `Sentry.captureMessage`). Introducing sentry_flutter test fixtures just to assert one warning was emitted = overcomplication (Karpathy #2). The `@visibleForTesting` static hook is 5 lines of code total: production path is identical (`Sentry.captureMessage` when hook is null), test path captures the warning into a `List<String>` for assertion. Deterministic, no SDK init.

3. **Wrapped BOTH orchestrator entry points (generateChat + generateNarrativeComponent), not just generateChat.** The PLAN.md task 2.2 only described `generateChat`; but `generateNarrativeComponent` carries the SAME `_calibratedArchetypes` guard (added in plan 02-03 Task 5). If only `generateChat` is wrapped, the rollback creates inconsistent behavior: chat is bypassed (calibrated archetype refused = false) but dashboard narrative cards still refuse with the « pas encore calibré » fallback. That's a bad rollback contract — operators flipping the flag expect ALL coach surfaces to render. Rule 2 — Missing critical functionality (consistency requirement).

4. **Idempotency on the Sentry warning emission.** Only the `true → false` transition emits the warning. `false → false` (e.g. flag has been disabled for 24h and the server keeps returning false at every 6-hour refresh) does NOT re-emit. Without this, on-call would receive 4 warnings/day for a single rollback decision — Sentry noise that obscures real signals. The 5th test (`false → false (no transition) does NOT emit a warning`) pins this.

5. **Kept `evaluateCoachArchetypeGate` flag-agnostic.** The pure helper from plan 02-03 has signature `(CoachProfile profile) → CoachArchetypeGateVerdict`. Adding `FeatureFlags.enableCoachHardGate` as a side input would either: (a) require every caller to pass the flag (verbose, error-prone), or (b) read a static from inside the helper (couples a pure function to global state, breaks the existing 5/5 test pattern that constructs profiles in isolation). Instead, the flag check is at the SINGLE call site in `coach_chat_screen.dart:1671` — `gate.shouldBlock && FeatureFlags.enableCoachHardGate`. Same outcome, simpler design, no caller burden. Karpathy #2 (Simplicity First).

6. **Did NOT wrap the WaitlistScreen / /waitlist route / archetype refresh handler.** PLAN.md task 2 step 2.3 explicitly states: « The flag is purely a wrapper. Do NOT add a wrapper at any other site than the 2 documented gates (the WaitlistScreen itself stays accessible regardless of the flag — it's a public destination). » Followed exactly. The /waitlist route is `RouteScope.public` (plan 02-03 Task 3) — reachable unauthenticated and unredirected — independent of the gate.
