## Codex verdict (external CLI — OpenAI Codex)

**Recommendation : Atomic PR-2 (full hard-gate path).**

> A split leaves you in a legally and technically worse transitional state because the current defect is known, reproducible, and tied to user-harmful advice routing. PR-2a is not truly additive : adding `unknown` and `usTaxPerson` changes behavior immediately and creates new partial-state failure modes (exhaustiveness gaps, silent defaults, precision regressions, persistence drops). A temporary « toast refusal » without full routing/gating/waitlist plumbing is a weak control because it is presentation-layer only and easier to bypass through stale state or alternate entry points.
>
> For this class of P0 compliance bug, the only defensible posture is one deployable unit where detection, persistence, routing gate, backend defense, and UX containment land together.

### 4th risk (R4) — Backward compatibility + stale persisted profile migration hole

> Users already have serialized profiles (local storage/server payloads) created before `usTaxPerson`/`unknown`. If deserialization defaults or migration paths treat missing `usTaxPerson` as falsy or map unknown archetype to legacy Swiss-native logic, the gate can be bypassed for existing users even after atomic merge.

**Mitigation** :
1. Treat `usTaxPerson` as tri-state (`true/false/null`) end-to-end ; never coerce null to false in gate logic.
2. On app start/profile load, run explicit migration : recompute archetype with strict null semantics and force gate evaluation before coach access.
3. Add regression tests for « old JSON without new keys » and « cached pre-fix profile » flows.
4. Add telemetry counter : `gate_decision_by_signal_state` to detect unexpected pass-through.

### Panel review timing — AFTER (final integrated diff)

> For a compliance-critical, cross-cutting patch, authoritative review must happen on the final integrated diff because most failure modes are interaction bugs between patches (model propagation + gate + routing + backend fallback + i18n/walker). Parallel review of unfinished work is useful for early red flags, but it produces churn and false confidence when invariants are still moving. Use parallel comments as advisory, then run one strict composite panel on the completed branch before merge as the actual go/no-go artifact.

### Brutal honesty (R5) — Runtime kill switch required

> Your three internal verdicts are directionally correct, but still slightly optimistic unless you add **migration + observability** as release blockers. Without those, you can ship « fixed code » that fails silently on real cached users. Also, do not rely on « defense in depth » wording unless backend enforcement is hard-fail and test-proven ; otherwise it is just duplicated soft logic. Finally, if this is truly P0 legal exposure, **require a short-term runtime kill switch for coach advice rendering when archetype is `unknown` or signal set is incomplete**, so rollback pressure never reopens the exact same liability window.

## Gemini verdict (external CLI — Google Gemini)

**Recommendation : Atomic PR-2.**

> Splitting into PR-2a (additive) and PR-2b (functional) is an architectural trap. Dart's exhaustiveness checking for enums will force you to touch the consumption sites (switches) anyway, and shipping the detection logic without the UI gate creates a « Zombie State » where users are correctly identified as `unknown` or `expat_us` but then fall through to a broken or empty Coach experience. More critically, the « code-reviewer » agent is correct : without the full plumbing (`toJson`/`fromJson`), your security signal is transient and will be lost on the first app background/resume.

### 4th risk (R6) — Pydantic Schema « Data Erasure » Round-trip

> The internal agents focused on the Dart models, but they missed the backend schema gap.
>
> - **The Risk** : Even if you patch the mobile app's `toJson`/`fromJson` to persist `usTaxPerson`, the backend `Profile` schema at `services/backend/app/schemas/profile.py` does NOT contain these fields.
> - **The Impact** : When the mobile app syncs local data to the server via `claimLocalData`, the backend DB (SQLAlchemy `data` column) will save the field, but when the app fetches the profile back (e.g., on login or refresh), the FastAPI Pydantic schema will **strip the « unknown » fields** from the JSON response.
> - **Mitigation** : You MUST add `us_tax_person` and `nationality` to the backend `ProfileBase` and `ProfileUpdate` schemas in the same atomic window, or your FATCA signal will vanish every time the user syncs with the server.

### Panel review timing — AFTER (Final Diff)

> For a P0 legal fix involving « Defense-in-Depth », you cannot review the pieces in isolation. A parallel review of a work-tree in flux will miss the critical « leaks » between the detection logic, the persistence layer, and the UI gate. You need a holistic review of the final, merged diff to ensure that no path (GoRouter, Orchestrator, or PrecisionService) can accidentally serve content to a US person.

### Brutal honesty (R7) — Legacy User Lockout + String-slug killer

> The « String-slug » architecture in `precision_service.dart` and `prompt_registry.dart` is a **silent killer**. By defaulting to `swiss_native` logic in the `default` branch of string-based switches, you have built a system that « fails unsafe ». Adding `FinancialArchetype.unknown` is the right move, but if you don't explicitly handle `'unknown'` in every one of those string switches (returning `0` for LPP years, for example), you are just trading a legal bug for a calculation hallucination.
>
> Also, be prepared for **Legacy User Lockout** : changing the `nationality == null` fallback from `swissNative` to `unknown` will immediately kick every existing user who hasn't completed their profile to the waitlist. You are effectively forcing a « Hard Re-onboarding » for a large segment of your base. If you aren't ready for that churn, you need a migration flag.
