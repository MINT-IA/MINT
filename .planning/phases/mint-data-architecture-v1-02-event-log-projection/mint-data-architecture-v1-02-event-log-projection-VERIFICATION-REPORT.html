Lessons learned

  1. « Substrate landed » means « code merged » not « feature deployed ». Future phase plans should explicitly enumerate the deploy step (or the deferral to a deploy phase) in the autonomous: false / autonomous: true frontmatter.
  2. Preflight scripts must run BEFORE phase planning, not BEFORE PR merge. The preflight_zero_user_gate.py check would have surfaced « prod has 2 users + prod is at 29_05_magic_link_tokens head » during Plan 02 RESEARCH, not after substrate code merged. Phase 03 onward : include a « deploy environment state audit » as a Phase RESEARCH step.
  3. Railway service topology is non-obvious from the CLI. Staging has TWO Postgres services (Postgres empty + postgres-qdyu live). railway variables --service Postgres returns the empty one ; only railway ssh -e staging --service MINT reveals the live DB. Phase 02-deploy CONTEXT.md must document this.
  4. caplog fragility under pytest -x --cov — direct logger mocking via sys.modules[name].logger is the sequence-independent pattern. Future tests asserting log emission should prefer mock.patch over caplog.
  5. Split-phase doctrine. When the operational shape of a phase outgrows the original autonomous: false checkpoint discipline, splitting into substrate-phase + deploy-phase is cleaner than retrofitting. The substrate-phase closes ; the deploy-phase opens with full checkpoint discipline.
