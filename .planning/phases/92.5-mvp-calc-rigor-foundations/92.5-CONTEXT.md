# Phase 92.5: MVP-CALC-RIGOR-FOUNDATIONS — Context

**Gathered:** 2026-05-09
**Status:** Ready for planning
**Decision authority:** Product Leader Claude (Julien delegated full agency for engineering tradeoffs)

<domain>
## Phase Boundary

Make « calc engine = source de vérité » a **mechanically credible** claim before Phase 94 CITATION-GATE consumes calc outputs. Three independent grounding axes (differential Mobile↔Backend on existing parity surface, Hypothesis property suite, ESTV oracle pin) plus a 6th perimeter gate (G6 calc-correctness) that blocks merges touching financial_core/ or backend services when calculations regress silently.

**In scope:**
- Differential CI harness on the **existing parity surface** between Dart `financial_core/` and Python `services/backend/app/` (capital tax / LPP bonifications / RAMD couple cap helpers).
- Hypothesis property test suite (8 invariants) running against the Python helper functions that already exist + Dart-side Mobile invariants where Python parity is absent.
- ESTV oracle: 50 (input_profile, expected_tax) vectors captured from `swisstaxcalculator.estv.admin.ch` via Playwright headless, validated against MINT computed output.
- G6 calc-correctness gate added to PERIMETERS.md, scoped to PRs touching `apps/mobile/lib/services/financial_core/**`, `services/backend/app/services/**`, or `services/backend/app/constants/social_insurance.py`.

**Out of scope (deferred — see backlog 999.4 = new Phase 92.6 candidate):**
- Full Python backend port of `AvsCalculator.computeMonthlyRente`, `LppCalculator.projectToRetirement`, `TaxCalculator.capitalWithdrawalTax` (≈1227 LOC of Dart logic). No backend Python parity exists today; full port is ~1200 LOC of error-prone work that would introduce false-positive divergences and contradicts ADR-2026-02-23 (Mobile financial_core/ as canonical source).
- 999.x items (HMM regime-switching, NSGA-II Pareto, mint-wiring-verifier) — explicitly out of scope per ADR 2026-05-09 calc-first §Mapping.

**This is a foundation phase**, not a feature phase. Success = mechanical CI gates green on every PR, not user-facing UI.

## Implementation Decisions

### GA-1 — Backend Python calc-parity scope (BLOCKER, Product-Leader-decided)
- **D-01:** Differential harness ships on **existing parity surface only** (≈80–100 fixtures, NOT 200). Surface map:
  - `services/backend/app/constants/social_insurance.py:calculate_progressive_capital_tax` ↔ `apps/mobile/lib/services/financial_core/tax_calculator.dart:RetirementTaxCalculator.capitalWithdrawalTax` (full progressive bracket parity already exists)
  - `services/backend/app/constants/social_insurance.py:get_lpp_bonification_rate` ↔ `apps/mobile/lib/services/financial_core/lpp_calculator.dart:_getBonificationRate` (age→rate table parity)
  - `services/backend/app/constants/social_insurance.py:rente_from_ramd` ↔ `apps/mobile/lib/services/financial_core/avs_calculator.dart` couple-cap helper (RAMD ceiling parity)
  - `services/backend/app/constants/social_insurance.py:get_ai_rente_monthly` ↔ Dart equivalent if exists, else excluded.
- **D-02:** ROADMAP §92.5 success criterion #1 must be **patched** as part of plan 92.5-01 to reflect 80–100 fixtures, not 200. Patch authority granted by this CONTEXT.md.
- **D-03:** Full 200-fixture coverage including AVS rente projection + LPP retirement projection deferred to **new backlog item 999.4 « Phase 92.6 — Backend calc-parity scaffold »** (Python port of the 3 locked Dart calculator methods, ~1200 LOC, post-TestFlight, 4-6d). To be added to ROADMAP backlog as part of plan 92.5-01.

### GA-2 — Differential harness invocation mechanics
- **D-04:** Dart side compiled once per CI run via `dart compile exe apps/mobile/tools/calc_harness/main.dart -o build/calc_harness_dart` (a new ≈100-LOC Dart entrypoint that imports `package:mint/services/financial_core/...` and reads JSONL on stdin / writes JSONL on stdout).
- **D-05:** Python side: `services/backend/tests/test_calc_diff_harness.py` spawns the Dart binary **once** per pytest session (fixture-scoped subprocess), pipes the 80–100 fixtures as JSONL on stdin, parses JSONL output, asserts per-axis tolerance per ROADMAP §92.5 success criterion #1.
- **D-06:** Tolerances locked per ROADMAP: rentes ±1 CHF, canton tax ±5 CHF, small ratios ±0.05. Recorded in `services/backend/tests/test_calc_diff_harness.py` as module-level constants with citation comment.
- **D-07:** CI workflow `.github/workflows/calc-rigor.yml` runs in matrix `[3.5.x dart, 3.11 python]` ; binary build step cached on the Dart SDK + financial_core/ checksum to avoid rebuilds on no-op changes.

### GA-3 — Frozen 200-fixtures (now 80–100) provenance & schema
- **D-08:** Generation strategy: **deterministic matrix** — 8 archetypes × 5 cantons (ZH/VD/GE/BE/BS — top 5 by population) × 2 phases-de-vie (working_age / retirement_proche) = 80 fixtures. Optional +20 hand-curated edge cases (FATCA, frontalier, independent_no_lpp) = 100 max.
- **D-09:** Schema: JSONL one-fixture-per-line at `services/backend/tests/fixtures/calc_diff_v1.jsonl` with shape `{id, archetype, canton, age, gross_income, lpp_balance, marital_status, expected_axes:{...}}`. `expected_axes` is empty on first commit; populated by Mobile baseline run, then frozen.
- **D-10:** Lifecycle: any change to a fixture or to `expected_axes` requires a separate commit with prefix `fix(calc-fixtures):` and a one-line ADR note. Fixture file checksum tracked by lefthook lint to flag accidental drift.

### GA-4 — ESTV oracle capture method
- **D-11:** Method: **Playwright headless scraping** via a one-shot Python script `services/backend/tests/scripts/capture_estv_oracle.py` (≈50–80 LOC). Run manually by Julien once per ESTV publication cycle (typically Nov–Dec when new tarifs publish). Output: `services/backend/tests/fixtures/estv_oracle_2025.jsonl`.
- **D-12:** Profile selection: 5 cantons (ZH/VD/GE/BE/BS) × 5 marital/income combinations × 2 ages = 50 vectors exact.
- **D-13:** Staleness flag: `expected_capture_date` field on each vector + lint `tools/checks/estv_oracle_freshness.py` that WARN-only if any vector is older than 14 months. WARN, not FAIL — annual capture cadence + occasional ESTV downtime should not block CI.
- **D-14:** Test runner: `services/backend/tests/test_estv_oracle.py` matches MINT computed value (via Python `calculate_progressive_capital_tax` + cantonal multiplier from existing Python helpers) against ESTV expected within tolerance ±5 CHF (same as differential cantonal tax tolerance). If MINT and ESTV disagree, the test FAILS — never silently passes.

### GA-5 — Hypothesis property suite (CALC-02)
- **D-15:** Suite location: `services/backend/tests/test_property_invariants.py` using `hypothesis>=6.111` (new dep, add to `services/backend/requirements.txt`).
- **D-16:** 8 invariants cover only the **Python parity surface** (capital tax progressive, LPP bonification rate, RAMD couple cap, AI rente). Mobile-only invariants (AVS computeMonthlyRente, LPP projectToRetirement) tested in a parallel Dart test file `apps/mobile/test/financial_core/property_invariants_test.dart` using a Dart fuzz library (decision: ship pure-Dart loop with seeded `Random`; full Hypothesis-equivalent in Dart not available, ship deterministic 1k-iteration loop instead).
- **D-17:** Hypothesis settings: `max_examples=200`, `deadline=None` (calculations are pure, can be slow on CI). CI profile: `--hypothesis-profile=ci` overrides to `max_examples=500` for nightly.

### GA-6 — G6 gate wiring & blocking policy (CALC-04)
- **D-18:** PERIMETERS.md schema extension: add G6 row to the gate table:
  ```
  | G6 | Calc-correctness CI (calc_diff + property + ESTV) | run id of .github/workflows/calc-rigor.yml |
  ```

  Add note: « G6 applies only to perimeters/PRs touching `financial_core/`, `services/backend/app/services/`, or `app/constants/social_insurance.py`. Other perimeters remain on G1–G5 unchanged. » No remplacement of G1–G5.
- **D-19:** Blocking policy: **hard-block from day 1** on PRs that match path triggers. No warn-only ramp-up — silent drift is the failure mode we are explicitly preventing. Path detection by GitHub Actions `paths:` filter on the workflow.
- **D-20:** Failure UX: when `calc-rigor.yml` fails, the PR check writes a Markdown comment with the divergence axis (rente / tax / ratio), the fixture id, and the Mobile vs Backend values. Comment template at `.github/workflows/calc-rigor-failure-comment.md`.
- **D-21:** Orchestrator integration: `verify_phase_goal` step (in GSD verifier) calls G6 for any phase whose plan touches the trigger paths. Phases that don't touch calc paths skip G6 silently.

<specifics>
## Specific Ideas

- **Mobile is canonical, period.** When differential disagrees, default presumption = Backend Python helper has drift, NOT Mobile. Failure-comment template (D-20) reflects this asymmetry: « Mobile (canonical): X, Backend (under test): Y, divergence: |X-Y| > tolerance ».
- **Don't mirror Dart calc to Python.** This is the trap the ROADMAP author may not have seen — full mirror = 1200 LOC of port = 4-6d alone = doubles phase budget AND introduces porting bugs that look like Backend regressions to G6. Phase 92.6 in backlog 999.4 will only be triggered if/when Phase 94 CITATION-GATE proves Backend MUST compute (e.g., for citation_allowlist generation that requires server-side numbers).
- **ESTV oracle is the « real-world » axis.** The other two axes (differential + property) are internal consistency. ESTV is the one external check. If Backend agrees with Mobile but disagrees with ESTV, the bug is upstream of both — likely a stale federal/cantonal constant in `social_insurance.py`. Annual re-capture cadence is the remediation.
- **Citation discipline (per CLAUDE.md §9).** Plan 92.5-04 close-out cannot claim « G6 ready » without (a) `gh pr view` mergedAt non-null, (b) at least one observed CI run on `calc-rigor.yml` with green status posted to a real PR, (c) PERIMETERS.md committed with G6 row. Three deterministic citations or no « ready ».

</specifics>
