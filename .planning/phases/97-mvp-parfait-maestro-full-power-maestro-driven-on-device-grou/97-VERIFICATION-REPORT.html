W7 iteration cycle #7 — B004 close-out (2026-05-11)

Bug closed : B004 (P1 security — core/auth.py:55 bare except Exception: pass swallowed JTI-blacklist DB errors. Under SQLAlchemyError from is_jti_blacklisted(db, jti), the revoked-token check failed silently and the flow fell through to decode_token() which accepted the still-validly-signed token. Result : auth-bypass via infrastructure degradation — a revoked JWT could authenticate under DB stress).

Fix shape : Replace the bare except with two specific clauses. except pyjwt.exceptions.PyJWTError: pass preserves the intended decode-fallback path (a malformed token still gets a clean 401 via the canonical decode_token() at line 58). except SQLAlchemyError: logger.exception(...); raise HTTPException(503, "Service de blacklist temporairement indisponible") makes the system fail-CLOSED on infra degradation — industry standard for auth-revocation surfaces. Better to refuse a valid token than to accept a revoked one when revocation cannot be verified.

Methodology continuity : Second unit-test-gated bug closure of W7 (after T001). Auth dependencies have no Maestro-reproducible UI surface ; the test mocks is_jti_blacklisted at the HTTP-dependency layer and asserts response status codes. The 7-step cycle still applies — REPRO authored a failing pytest (test 1 FAILS RED with explicit auth-bypass body), FIX makes it GREEN, LOCK adds the test path to the « Unit-Test-Locked Bugs » section of tools/simulator/flows/regression/_INDEX.md. Pre-commit + CI pytest -q is the regression gate.

Operator constraints honored : Karpathy #2 simplicity-first (2 specific except clauses, no defensive layering, no circuit-breaker, no retry harness — the surgical fix the audit asked for). Karpathy #3 surgical (ONLY 2 files touched : services/backend/app/core/auth.py + new services/backend/tests/test_auth_jti_blacklist_silent_fail.py). CLAUDE.md rule 1 banned-terms clean. CLAUDE.md rule 2 accent FR clean (« Token révoqué » preserved with accents, « Service de blacklist temporairement indisponible » accent-correct). CLAUDE.md §9 0-trust — no « shipped » claim without the pytest receipt cited above.

Honest disclosure : The fail-closed 503 is intentionally aggressive. In production, a sustained DB outage at the blacklist surface WILL cause user-facing 503s during authentication — this is the correct trade-off for a revocation surface, but ops must be aware. A circuit-breaker / retry harness was NOT added in this surgical fix (would require Redis or in-process state, out of scope for Karpathy #3). The Sentry breadcrumb auth.jti_blacklist.db_error emitted via logger.exception gives operations a triage signal if 503 spikes appear.
