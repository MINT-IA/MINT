## P2 Findings

### P2-a — `fiscalite` block "complete" + active tax-document Ask (UX tension, not a safety issue)

**Evidence:** `confidence_scorer_test.dart:885-913`

When `typedTaxProfile && documentTaxAssessmentEnabled` are both true, a user who scanned an `assessedAppealable` assessment with all amounts present will see `fiscalite` block score 15/15 (`status: 'complete'`) while the `tax.document.review` prompt is still active. `scoreAsBlocs` measures data presence; `_hasPrecisionReadyTaxDecision` measures documentary quality (requires `inForce + attested + exact UUID coherence`). These are different quality axes, and the design is intentional, but a user seeing "complete" alongside an active data-collection prompt for the same domain may dismiss the prompt.

This is behind default-off flags and does not affect safety. Clarify the two-quality-axis UX (data completeness vs. source finality) in copy before activation.

### P2-b — No automatic staleness for `pillar3aBeneficiaryClause` after OPP 3 June 2027

**Evidence:** `swiss-domain-verdict.md §17/18/21`; `specialist_reference_contract_test.dart:'calendar-year change alone does not stale durable references'`

The `stateAt` method no longer checks `legalYear != civilAsOf.year`. For `pillar3aBeneficiaryClause`, this is intentionally correct (the diff's addendum: "c'est l'entrée en vigueur effective qui doit piloter l'invalidation"). However, the OPP 3 modification entering into force on 2027-06-01 will change beneficiary-clause rules in a way the current code cannot auto-detect. The test `RETREF-D09` describes the expected stale behavior but there is no code that sets the clause stale when the legal event fires. Resolution: tracked by the existing product process; not a pre-activation blocker for the fiscal reference scope, but the activation checklist should include a dated reminder.

### P2-c — `latestTaxDecisionReference` dual serialization path

**Evidence:** `coach_profile.dart:4431` (`fromJson` reads it), `coach_profile.dart:4575` (`toJson` writes it), `coach_profile.dart:5410` (`fromWizardAnswers` re-derives it)

The docs explicitly state it is "not an independent persistence authority," and the `stateAt` coherence check (`taxSnapshot.updatedAt.toUtc() == confirmedAt.toUtc()`) would fail for a stale JSON-serialized reference. No functional risk has been identified, but future maintainers may find the dual path confusing. Document the canonical authority ordering in a comment at the `fromJson` call site.

### P2-d — Maestro `landing_route` assertion (good defensive fix, already in the diff)

## MINT product logic review

This change moves squarely along the **ledger → DataQuest → scenario → dossier** spine:

- **Ledger**: `latestTaxDecisionReference` is derived metadata over the single `_coach_tax_snapshots_v1` root, not a second ledger. No new persistence key, no backend mirror, no financial calculation.
- **DataQuest**: The diff reuses the existing `EnrichmentPrompt.taxDocument` and `fiscalite` DataBlock. No new DataQuest service or Case is introduced. The prompt closes only on exact reference coherence (UUID + sourceDate + confirmedAt + inForce + attested).
- **Scenario**: Not consumed by any scenario yet; the reference is status-only for the current confidence scorer scope. No scenario is broken.
- **Dossier/specialist handoff**: The reference tuple (UUIDv4, kind, period, canton, subject, source date) is exactly what a specialist PDF would need to locate the authoritative document. The handoff boundary is clean.

One implementation detail to verify pre-activation: `_hasPrecisionReadyTaxDecision` runs a precise selector requiring `cantonalCommunalTaxableIncomeChf`. A user with a valid `inForce` decision that omits income (only wealth or only rate) will have a reference built (private selector doesn't require income) but will still see the tax-document prompt (because the precise income query fails). This is intentionally conservative and consistent with the "reference alone doesn't mean the data block is complete" design, but the prompt should eventually be decoupled from the income-field gate once the domain can express "final reference present but income still needed."
