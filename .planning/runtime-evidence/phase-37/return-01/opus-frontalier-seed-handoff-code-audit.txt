# MINT External Audit — G1-RETURN-01 six-origin runtime harness

**Scope:** 4 worktree-modified files (Patrol integration test, Dart runtime contract test, Python orchestrator test, orchestrator shell script). Reviewed against the on-disk source of truth, not just the diff.

## What the change does
1. **`patrol_test.dart`** — teardown no longer unconditionally clears diagnostic state; it now *preserves* the synthetic seed for exactly `housing_cancel` and `frontalier_inline` (`_maestroSeedStages`, lines 26-29, 77-81). The pre-stage `clearDiagnostic()` (line 84) is retained.
2. **`patrol_return01_six_origin.sh`** — `restore_normal_build()` now terminates → **uninstalls** → asserts the container is gone → installs the normal app → launches (lines 216-232). New `restoration-uninstall.log` added to the artifact allowlist (line 776).
3. **Test files** — added structural assertions locking the teardown-preservation shape and the uninstall-before-restore ordering.

## Correctness / coherence verification
- The Dart `_maestroSeedStages` set (`housing_cancel`, `frontalier_inline`) **exactly matches** the shell `run_maestro_stage` branch that sets `synthetic_seed='preserved'` and refuses to uninstall (`patrol_return01_six_origin.sh:475-483`). The other three stages (`work_save`, `disability_validation_cancel`, `succession_save`) uninstall for a clean install (lines 465-474) and are correctly excluded from the seed set. This resolves a prior inconsistency where teardown wiped the seed the Maestro overlay stage expected to fingerprint.
- Seed does not leak across stages: every Patrol stage re-clears at start (`patrol_test.dart:84`); the `disability`/`succession`/`work` Maestro stages uninstall first. The final `restore_normal_build` (line 858) now uninstalls, so no synthetic seed survives into the "restored production" app — a genuine privacy/cleanliness improvement, not a regression.
- New `restoration-uninstall.raw.log` is routed through `sanitize_log` (lines 228-229) and is allowlisted (line 776); `verify_privacy_inventory` scans it. No raw private path exposure. The failure-path message is appended only to the raw log and only when the function `return 1`s, so it is never emitted to `$artifacts`.
- Test↔implementation alignment confirmed line-by-line: ordering `terminate<uninstall<absence_check<install<launch`, the two-line `sanitize_log` continuation, `restoration_status='restored'` after launch, cleanup guards, `trap cleanup EXIT` before `export_physical_source()`, and the allowlist regex token all match the actual script.
- Referenced Maestro flows and the RVC runner exist; the runtime test's `.maestro/…` relative paths resolve under `apps/mobile/` (its cwd), consistent with the orchestrator's `apps/mobile/.maestro/…`.
