Product/domain verdict: NO-GO

This slice wires the pre-existing certificate-only `AvsGapEvidence` into `RetirementProjectionService`, so that AVS (and with it the *entire* household retirement projection) is suppressed unless the AVS contribution gap is certificate-sourced. The gating logic itself is internally consistent and conservative, but it was only half-migrated and it discards value the product already had. The result is a duplicated AVS source of truth and a silently-degraded flow. No P0 (the change refuses rather than misleads), but multiple P1s.

## P1 — product/domain incoherence

**1. Two divergent AVS truths for the same household (duplicated source of truth).**
`RetirementProjectionService.project` now suppresses AVS unless certified (`retirement_projection_service.dart:205-206`, gating totals/gap/phases at `:222`, `:238-271`). But `ForecasterService` — which feeds the actual `/retraite` dashboard (`retirement_dashboard_screen.dart:342,453`) and the home-state `replacementRate`/`friScore` (`mint_state_engine.dart:164-165,169-174`) — still estimates AVS from `lacunesAVS ?? 0` with **no** certificate requirement (`forecaster_service.dart:823,841`).
Repro: a user with salary/LPP/3a but no uploaded *extrait de compte AVS*. `MintStateEngine` computes `replacementRate`/`friScore` **including** estimated AVS (Forecaster), while `budgetGap` is forced to `null` because `avsIncluded == false` (`mint_state_engine.dart:189-195`). Home shows an AVS-inclusive replacement rate/FRI, but the AVS-inclusive budget gap vanishes — same profile, same screen, contradictory AVS treatment. This violates the ledger "one source of truth" spine.

**2. Valid LPP/3a/patrimoine projection is thrown away with AVS (route delivers no value).**
When AVS is uncertified, `revenuMensuelHorsAvs` (LPP+3a+libre, which need *no* AVS certificate) is computed (`retirement_projection_service.dart:219-224`) but **no consumer reads it** (grep: only `budget_living_engine`, `mint_state_engine`, tornado read the result, none read `revenuMensuelHorsAvs`). `BudgetLivingEngine` collapses to `BudgetStage.presentOnly` on `!avsIncluded` (`budget_living_engine.dart:62,111`), and the test locks this in (`retirement_projection_service_test.dart:90,98-101,156` — `revenuMensuelHorsAvs > 0` yet `phases`/`budgetGap` empty). Since most users have not uploaded a certified AVS extract, the common case loses its entire retirement picture even though LPP/3a are fully computable — a facade-without-wiring (`revenuMensuelHorsAvs`) and a route that stops delivering understanding.

**3. Missing-data reason is computed then dropped — no DataQuest handoff.**
`missingFields` (`['prevoyance.lacunesAVS']`) is populated on the result (`retirement_projection_service.dart:281`) but **no UI reads `avsIncluded` or `missingFields`** (grep confirms). `BudgetLivingEngine` returns generic `presentOnly` — indistinguishable from the "no salary / no age" degraded case (`budget_living_engine.dart:62-68 vs 100-108`). The user is never told "certify your extrait de compte AVS to unlock your retirement projection." This is precisely the missing-data / specialist-handoff state the product model requires, and it is silently lost at every boundary.

**4. Concubinage: spouse AVS certificate wrongly required (métier incoherence).**
`spouseRequired = isCouple` (`coach_profile.dart:2030`), and `isCouple` includes concubinage (`coach_profile.dart` `isCouple` getter = `marie || concubinage`). Via `householdReady` (`coach_profile.dart:77-78`) this blocks the user's *own* projection until the partner's AVS gap is certified. For concubines the 150% couple cap does **not** apply (LAVS art. 35, correctly noted at `retirement_projection_service.dart` income block) and each rente is strictly individual — the partner's AVS gap is irrelevant to the user's own rente. Blocking the whole household output on it is domain-incoherent. The same edit also drops the prior `&& conjoint != null` guard, so a couple profile with no conjoint object at all now blocks entirely rather than projecting the known side.

## P2

- `_computeEarlyRetirementComparisons` recomputes `avsIncluded` internally (`retirement_projection_service.dart:1000,1044-1046`), but the function is only invoked when `avsIncluded` is already true (`:249`), so the internal branch is dead code.
- `TornadoSensitivityService.compute` (this diff's `_project` now returns `nan` when `revenuMensuelAt65 == null`, `tornado_sensitivity_service.dart`) has **no production caller** (grep: 0 hits in `lib/`; the code's own comments say "no production renderer"). The empty-list-on-uncertified-AVS behavior is test-only — not a user regression, but the added `// lint-ignore: dormant` labels confirm dead surface that should be tracked, not shipped as "production."
- Commit message "audit-slice: AVS production with final tests" touches zero test files in the slice; the locking tests live in the baseline commit. Naming overstates what this slice contains.

## Swiss domain review
- **AVS**: Behavior change is the whole point. Certificate-only gating is a defensible compliance stance in isolation, but it is applied inconsistently (Forecaster still estimates AVS ungated) and destructively (kills LPP/3a output too). 13th rente (LAVS art. 34), 150% couple cap (art. 35), anticipation/ajournement, AVS21 gender-aware age — all preserved unchanged in the gated branch; concubinage handling is domain-correct in the income math but wrongly gated (P1 #4).
- **LPP / 3a / libre**: Calculations unchanged and independent of the AVS certificate, yet suppressed alongside AVS — the core lost-value defect. Conversion-rate (LPP art. 14), LIFD art. 38 capital tax, SWR-not-income all intact.
- **Tax / mortgage / insurance / succession / disability**: Not touched by this diff.

## Mint product logic review
This moves *against* the ledger → DataQuest → scenario → dossier spine. It creates a second AVS truth (Forecaster estimated vs. RetirementProjection certified), collapses the scenario surface to present-only for the majority who lack a certified AVS extract, and computes but discards the exact missing-field signal (`missingFields`, `revenuMensuelHorsAvs`, `avsIncluded`) that a DataQuest prompt or dossier caveat would need. To become a PASS: surface `avsIncluded == false` as an explicit "AVS estimated / upload extrait de compte to certify" state that still renders the LPP/3a/libre projection (`revenuMensuelHorsAvs`), and either migrate Forecaster to the same rule or clearly label both as estimates so the household sees one coherent AVS story.
