## Bug A — Coach « pas disponible » pour user authentifié

**Reproduction**: log in on TestFlight v2.12.3 (build 42), open chat, ask any question.
**Observed**: « Le coach IA n'est pas disponible pour le moment. » template renders (citation: `apps/mobile/lib/services/coach/coach_fallback_messages.dart:31`).
**Expected**: coach answers normally.

**Mechanism (code-grep evidence)**:
- `apps/mobile/lib/services/coach/coach_orchestrator.dart:349-370` — fix B13 du 2026-05-09 (commit `60e14c12`) skips tier 3.5 (anonymous chat) for logged-in users. Comment line 360-365: « tier3.5=Anonymous skipped (user is logged in) ».
- Falls through to line 369-370: « ALL TIERS FAILED — returning fallback » → `_chatFallback(language)` → the « pas disponible » template.
- Working tier 1 (BYOK): out of scope per memory `project_byok_scope.md` (skipped for QA).
- Working tier 3 (server-key): probable failure mode — see suspects below.
- Tier 3.5 (anonymous): explicitly bypassed for logged-in users.
- Tier 4 (template): the message Julien sees.

So the broken tier is tier 3 (server-key, the `/coach/chat` Railway endpoint).

**Suspects (ordered by likelihood — Anthropic key on Railway is NOT one of them, it's there)**:
1. **Dual-LLM split shape regression** — PR `b88e8d23 feat(91-02): wire dual-LLM extractor + narrator surface narrowing (Wave 2)` shipped 2026-05-08+. If response shape now has `extractor_response` + `narrator_response` separately and the Mobile parser still expects `message`, every reply parses as empty → `coach_orchestrator.dart:975-978` returns null → fallback. Verify: a single end-to-end POST to `/coach/chat` with auth bearer, inspect JSON shape vs `CoachChatApiService.sendChatMessage` deserializer.
2. **Auth token not propagating** — server-key tier requires the user's bearer; if a recent fix broke token forwarding, backend returns 401 → exception path → fallback. Verify: backend logs for 401s on `/coach/chat`.
3. **Tool-call parser crashes on empty toolCalls** — `coach_orchestrator.dart:982-994` iterates `response.toolCalls`. If shape changed and `toolCalls` is null instead of `[]`, throws → catch line 1022-1024 returns null → fallback.
4. **Backend `/coach/chat` raises 5xx silently** — could be a recent backend code change that throws on the auth user's request payload (e.g., missing field, archetype detection failing on Julien's profile). Verify: Railway staging logs filtered by Julien's user_id at the timestamp of his test.

**Test plan to confirm**:
- Tail Railway staging logs for the last 30 min while Julien re-tests on his device.
- Repro on iOS sim with Maestro flow against staging — but the bug is logged-in only, requires auth flow setup on sim. Not trivial.
- Easier: `curl -X POST https://mint-staging.up.railway.app/coach/chat -H "Authorization: Bearer <julien-token>" -H "Content-Type: application/json" -d '{"message":"test","language":"fr"}'`. Inspect status + body shape.

## Bug B — Logout ne reset pas la session anonyme du chat

**Reproduction**: log in, open chat, send messages → log out → land on landing screen → tap « Parler à Mint » → arrives on the OLD chat thread (not a fresh anonymous session).
**Observed**: previous conversation history shown, with the « pas disponible » template at the bottom.
**Expected**: tap « Parler à Mint » from landing → fresh anonymous chat (3 free messages, fresh UUID session per existing anon flow).

**Mechanism (hypothesis, not yet code-grep-confirmed)**:
- Logout doesn't clear the chat repository's persisted state (likely `shared_preferences` or local DB key for chat history).
- OR the « Parler à Mint » CTA from landing routes back to `AnonymousChatScreen` with the same session UUID instead of generating a fresh one on landing-entry.
- Recent commit `47730781 fix(anon-chat): prevent permanent lockout when 200 OK drops messagesRemaining (BUG-P1-A02) (#518)` may have introduced or exposed this — needs a diff inspection.

**Test plan to confirm**:
- `grep -rn "AnonymousChatScreen\|kAnonChatSessionUuid\|anon_chat_session" apps/mobile/lib/` to find the session-key handling.
- Inspect `LandingScreen` CTA action handler — is it pushing to a fresh route or restoring from cache?
- Inspect logout flow: `apps/mobile/lib/services/auth/` — does it call any chat-cache-clear method?

## Bug C — Onboarding entirely missing on v2.12.3

**Reproduction**: log out and try to re-onboard → onboarding flow doesn't start, lands directly on `LandingScreen` or directly back into authenticated home.
**Observed**: « il n'y a plus de onboarding » / « on a perdu la trace de l'onboarding ».
**Expected**: fresh onboarding flow on logout-then-reopen, or on first-launch after logout.

**Mechanism (hypothesis, not yet code-grep-confirmed)**:
- Recent commit `dc987c4c fix(coach): onboarding crisis hotfix bundle B1-B6 (#529)` — the « hotfix bundle » naming suggests turbulent edits to onboarding routing. May have broken the entry condition.
- OR a redirect callback in `app.dart` (memory mentions `redirect:` callback at `app.dart:177-261`) is short-circuiting onboarding for users who completed it once.
- OR a feature flag or `seenOnboarding` boolean is sticky across logout.

**Test plan to confirm**:
- `grep -rn "seenOnboarding\|hasOnboarded\|onboardingComplete\|kOnboardingDone" apps/mobile/lib/` for the gating flag.
- Inspect `app.dart` `redirect:` callback for onboarding short-circuit logic.
- Check what logout actually clears (vs persists) in shared_preferences.
